# Tech Docs Blog Writing

只写读者愿信、愿照着做的技术文档与工程博客。一处假证据毁掉整页。科技风简洁：无过程性废话。

**博客第一要义：把一件事说清楚。** 哪怕只是一个很小的 bug，说透机制、复现与修法就够。不为「像一篇完整博文」而堆背景、堆三点启示、堆无关横评。能短则短；多出来的段落若删掉不影响那一件事，就删。

去 AI 腔靠**改写法**，不靠换同义词。成稿后必须跑一遍下方「去 AI 腔」。

## 模式

| 模式 | 做 |
|------|----|
| 起草 | 定件 → 选题 → 体裁 → 主张账本 → 写 → 门禁 |
| 修订 | 先问「读者多知道了什么」；说不清就别改。门禁 + 文风扫描，按 P0/P1/P2 列问题。未经允许不全文重写。等量替换不是目标 |

## 定件（能推断则不问）

体裁、读者、一句收获（必须是判断，不是复述）、证据边界、发布面。

没有**意外 / 测量 / 强观点**之一：直说不值得写，帮找角度。

中文必须有实践增量：命令、**版本号**、**错误码**、数字、失败路径、配置坑。

## 选题（博客必过）

反直觉 / 反叙事 / 意外能力 / 精确定名 / 共鸣——至少一条。

一事一篇：先写下「这一篇只回答哪一个问题」。答完即停。素材只够讲清一个小坑时，发短文；不要为凑体裁表去补 How We Built It / 横评节。

## 体裁（一页一事）

### 文档

| 类型 | 骨架 |
|------|------|
| Tutorial | 结果预览 → 前置 → 可验证分步 → 完整代码 → 下一步 |
| How-to | 目标 → 前提 → 步骤 → 验证 → 失败 |
| Reference | 按 API/表面穷尽；条目可独立引用 |
| Conceptual | 是什么 → 为何 → 模型 → 例子 → 何时不用 |
| Troubleshooting | 症状 → 排查树 → 修复 → 预防 |

标题：**一个主张**（用户问题形或结论形）。开头一段 TL;DR / 先给结论。

### 博客（有素材才选）

| 素材 | 模式 | 可信度靠 |
|------|------|----------|
| 时间线+意外 | 踩坑 | 死胡同 |
| 易错概念 | Explainer | 常见误解 |
| 系统+决策 | How We Built It | 取舍 |
| 前后数字 | Rewrite | 变糟之处 |
| 多事故同题 | Lessons | 每条一个故事 |
| 对比测量 | 横评 | 方法学先于结果 |

默认节序（仅当那一件事需要时才全用）：问题 → 怎么工作 → 取舍 → 怎么用/复现 →（深挖）失败与极限。小 bug 文可以只有：现象 → 复现 → 根因 → 修法。

## 主张账本

每条断言标一类：`Measured` | `Shown` | `Sourced` | `Opinion`。

无类：删 / 降为 Opinion / 补证据。性能主张最严。

横评先披露：硬件、版本、负载、配置、复现方式。

## 起草硬规则

1. 先工件后解释；开篇先结论
2. 每篇有明确判断，具体到版本号与错误码
3. 标题只放一个主张（禁「背景/架构/总结」、禁 Q&A 式 H3）
4. 数字压过形容词；条件式选型，不排名
5. 代码可运行，标语言；注释写 why
6. 有决策就写没选什么；优劣写可验证事实与具体代价
7. 一节一事；转折另起段

读者用「你」；步骤祈使。「我们」仅真实团队行为。

## 禁（营销/夸大）

兴奋宣布、业界领先、赋能、无缝、easy/simple、显著/大幅、最完整/最成熟/最优解/无可替代/极致、本文将探讨、众所周知、至关重要、希望对你有帮助。选型不写成排名。

## 去 AI 腔（必跑）

### 怎么写才不像

1. **先钉事实再写句**：每段先落下代码/命令/版本/错误码/数字，再围着它写；缺细节就问或写短句，禁止用空话垫场。
2. **一句一个新信息**：读上一句后仍成立的句子删掉（复述、金句收束、`这很重要`）。
3. **直接说正事**：默认不用「不是 A，而是 B」「不仅…而且…」；只有在纠正读者真实误解时才保留否定半句。
4. **整句重写，禁止换词**：标出腔调后，按主张重写整句/整段，不要只把「赋能」换成「帮助」。
5. **工整即腔，故意不齐**（见下节）。
6. **判断落在机制上**：先写约束/成本/失败路径，再下判断；不写「格局/赋能/至关重要」。
7. **中文母语顺序**：拆掉「对于…来说」「基于…」「使得…得以…」；主语+动作，少翻译腔长串。
8. **有样本跟样本**：用户给过往文章则跟其句长与口吻；否则技术文保持工程师直说，博客可保留真实「我/我们试过失败」，禁止伪造人设。

### 工整即腔

模型默认选「最对称、最好扫、最可预测」的结构。技术文要**可导航**，不要**版式对称**。

| 该留（导航） | 该打散（对称） |
|--------------|----------------|
| How-to 步骤编号、参考条目穷尽 | 连续 ≥3 节同一骨架（定义→三点→小结） |
| 表格比能力、清单列前置条件 | 句句差不多长；处处三项排比 |
| 一页一事、H2 可读 | 每节都「先概念后例子后启示」 |
| 代码块语言标签 | 段末固定金句/拔高；先…再…最后…串全篇 |

做法：

1. **测可预测性**：遮住下一节标题，若能猜中写法（又是三点+小结），合并、删一节或改成「失败/例外/数字」节。
2. **两项优于三项**：非必要不凑满三点；第三点往往是填充。
3. **句长错落**：相邻两句不要同长同构；允许一句极短跟一句带条件的长句。
4. **节长随内容**：重要节可以长，次要节三五行；禁止为版面把各节裁成一样厚。
5. **列表有门槛**：≥3 项且无序/有序才列表；两句能说完的不要拆成整齐 bullet 墙。
6. **Reference 例外**：查表页可以整齐；博客与概念叙述必须打破对称。

### 改写对照（技术文）

| 腔 | 改成 |
|----|------|
| 不是配置问题，而是发布过期 | 发布物过期了，配置没问题 |
| 至此我们完成了配置。接下来… | （删过渡）直接写下一步动作 |
| 没有错误。没有告警。一片绿灯 | 当时没有错误和告警 |
| 指标告诉你坏了什么，链路告诉你为什么 | 指标能定位异常面，根因要看链路 |
| 支持某某能力，提供灵活配置 | 打开 `foo.enabled`；超时默认 30s，可改 |
| 在快速变化的技术浪潮中… | （删）第一句写结论或故障 |
| 希望本文对你有帮助 | 复现脚本：`./scripts/repro.sh` |
| Keycloak 是最成熟的开源 IAM | Keycloak 自 2014 年维护；LDAP 联邦与细粒度授权开箱可用。选它当…条件满足时 |
| 三节都是「是什么→三点→小结」 | 一节给机制+版本，一节只写踩坑数字，小结只留有判断的一节 |
| 五个并列短句等长 | 合并相关句；留一句短的钉结论 |

### 扫稿顺序

1. 标腔：否定对照、金句收束、三拍碎句、总结式过渡、规格书腔、模板开场、破折号撑语气、**节/句对称过齐**。
2. 先打散工整，再按上表与「怎么写才不像」整段重写。
3. 核对事实未丢（版本、错误码、命令、链接）。
4. 出声读一遍；还能猜中下一节写法，或连续三句同构，继续拆。

去 AI 味时**不删**：技术名词（协议/产品/组件名，可挂括号）、mermaid/流程图图标、代码块示例输出、有真实判断的「小结」。

能力矩阵：不用 ✅❌⭐⚠️ 当状态；整格只有符号才改成「支持/不支持」等文字；符号后已有文字只删符号，勿反转语义。

## 出门

- [ ] 主张条条有证据；有判断；关键处有版本/错误码
- [ ] 开篇先结论；标题一个主张；H2 可读
- [ ] 已跑「去 AI 腔」；无营销/夸大；叙述节不对称过齐；术语未误删
- [ ] 代码可跑或已标明未跑；图与示例输出未被当装饰删掉
- [ ] 结尾有下一步，无复读
- [ ] 博客：一事说透；无堆砌；愿转给同事；否则进文档/changelog

交付时列出仍需人确认项。

## 协作（仅用户要一起写长文时）

上下文倾倒 → 分段打磨（定点改）→ 空白上下文读者测试。
